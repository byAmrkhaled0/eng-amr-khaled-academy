الحضور المقاس أعلاه هو المسار المتصل المتوافق مع السجل اليومي القديم؛ مسار QR المجهز ومعاملات جهازين اختُبرا سلوكيًا منفصلًا. القيم لا تشمل تشغيلًا باردًا حقيقيًا في Cloud Run، تحميل الخطوط، DNS أو TLS، جهازًا ماديًا، شبكة 4G أو CPU throttling.

اختبار متصفح IndexedDB: مسحان متزامنان لنفس الطالب والحصة → سجل واحد؛ استغرق الحفظ نحو 4ms في العينة المرئية. بقي بعد إعادة فتح الصفحة، ثم حُفظ إقرار الخادم التجريبي. اختبار الدفع في الواجهة استخدم تأخيرًا مصطنعًا 200ms وأكد دفعة 40/100. هذه ليست عينة P95.

اختبار Service Worker في VM مع كاش وشبكة مراقبة: طلب app.js المرتبط بالإصدار وهو مخزن مسبقًا سبّب اتصالًا خلفيًا واحدًا قبل التعديل وصفرًا بعده. API بيانات الطلاب لم يدخل مسار كاش الأصول. firebase-config.js ما زال network-first قصدًا. لا يوجد قياس ميداني لزمن الانتقال/التصفية أو رفع/استعادة ملفات كبيرة، ولا وعد أن كل زر أقل من ثانية.

الحجم لم ينخفض: مجموع JavaScript الأعلى في assets قرابة 825KB → 833KB، وgzip قرابة 219KB → 223KB؛ CSS قرابة 525KB → 527KB. هذه مجاميع ملفات وليست حجم التنزيل الأول؛ مكتبات vendor مفصولة ولا تدخل هذا الجمع. التحسن هنا من تصحيح الكاش وتقليل إعادة الحساب وإلغاء polling التقرير، لا ادعاء تقليل حجم الحزمة. فحص admin والـ QR المؤجل القائم حُفظ.

## نموذج عدد العمليات

N = الطلاب المحملون، M = ملخصات الفترة، D = عمليات اليوم في الفترة، R = سجلات الطالب، C = المحتوى المنشور، B = مستندات النسخة بما في ذلك الفرعيات. الأعداد التالية مراجعة لمسارات الكود، وليست تصدير Cloud Billing؛ أضف minimum query charge، قراءات القواعد، index entries، retries، والمشغلات المستقلة.

| الرحلة | الطلبات والقراءات/الكتابات المتوقعة | التغيير والحد الباقي |
|---|---|---|
| فتح الخزنة cold | 1 callable؛ نحو N+M+D+2 قراءة؛ لا كتابة | إجماليات كاملة؛ فلترة الفترة على الخادم، لكن تحميل كل الطلاب في cold ما زال مكلفًا |
| صفحات الخزنة داخل 15s | 1 callable/صفحة وقراءة صلاحية تقريبًا عند إصابة كاش نفس المثيل | 40 صفًا؛ cache مشتركة للفترة حتى 15 ثانية ولا تعتمد على جهاز العميل؛ بعد تبدل المثيل تعود cold reads |
| سجل دفعات طالب/فترة | 1 callable؛ صلاحية + حتى 41 مستندًا | 40 مع cursor؛ لا مسح سجل معاملات المنصة كله |
| إنشاء دفعة | نحو 5 قراءات أساسية، 6 كتابات للمعاملة والملخص ونسخ التوافق + سجل نشاط ومشغلات التقارير | retry لنفس requestId لا يكرر دفتر الدفع؛ لم تزال نسخ التوافق المالية القديمة |
| تحضير حصة | 1 callable؛ صلاحية/مجموعة/حصة + كامل طلاب المجموعة؛ كتابة تجهيز وحصة إن لزم | تجهيز محدد، لا مستمع roster دائم |
| مسح بلا شبكة | 0 طلب Firebase؛ معاملات IndexedDB | لا كلفة Firebase قبل المزامنة |
| مزامنة k حضور | ceil(k/60) طلبًا؛ تحقق التحضير مرة لكل دفعة، تحقق طالب/حصة وقراءات dedup لكل سجل؛ نحو كتابتين/سجل جديد + مشغل تقرير | الخادم يحسم تكرار جهازين؛ أخطاء سجلات منفردة لا تمس بقية الطابور |
| تقرير cold | 1 callable؛ R+C+جلسات المجموعات+قراءات الجلسة/النسخ + كتابة تقرير | أزيل إعادة بناء leaderboard لجميع الطلاب؛ لا تزال بعض استعلامات المحتوى وسجل الطالب تقرأ تاريخًا أوسع من الشهر |
| تقرير warm حتى 60s | جلسة/طالب + مستند التقرير ونسختي بيانات الطالب والمحتوى | قد تستلزم بيانات قديمة إصلاحًا إضافيًا في getStudentPortalByCode؛ تاريخ التحديث ظاهر |
| تغيير درجة | كتابة المصدر + marker لطالب واحد؛ التقرير التالي يعيد حسابه | لا إعادة حساب تقارير كل الطلاب عند تعديل درجة واحدة؛ حدث تغيير محتوى عام يبطل الكاش عند الطلب |
| نسخة يومية | نحو B قراءات + تعداد المجموعات الفرعية + رفع gzip واحد وbackup_runs | ليست لقطة ذرية مع كتابات متزامنة؛ التصدير يومي 02:30 القاهرة والاحتفاظ الافتراضي 14 يومًا |

مستمعا آخر 500 ملخص/معاملة أزيلا من شاشة الخزنة. أُزيل polling الدقيقة من شاشة تقرير ولي الأمر. بقية مستمعي الإدارة/المجموعات/الترتيب القديمة لم تُعد كتابتها كلها؛ يلزم قياسها في جلسة إدارة حقيقية. لم يضف minInstances. الإعداد العام 256MiB وmaxInstances=10؛ التقارير/الخزنة والتحضير 512MiB؛ استعادة واحدة لكل مثيل مع concurrency=1. لا نغيّر موارد الوظائف أو نسخها الدافئة بصورة شاملة دون Cloud Monitoring.

TTL جديد على expiresAt في _attendance_preparations (21 يومًا) و_attendance_requests (30 يومًا). انتهاء TTL ليس ضمان حذف فوري ولا بديلًا عن فحص صلاحية التاريخ في الخادم. السجلات المحلية المتزامنة لا تُحذف آليًا حاليًا؛ غير المتزامنة لا تُمسح عند الخروج. backup_runs/_restore_runs وسجلات التشخيص الأخرى تحتاج سياسة احتفاظ منفصلة؛ لم تُحذف بيانات موجودة.

## تقدير حسابي معلن

مثال افتراضي لشهر: 1000 طالب، 4000 حضور، 1000 دفعة، 4000 فتح تقرير، 900 فتح خزنة cold. نفترض 2036 قراءة/خزنة، 360 قراءة/تقرير، 7 قراءات/حضور و5/دفعة؛ الإجمالي التقريبي 3.31 مليون قراءة قبل النسخ وبقية البوابات والمستمعين. نفترض تقريبًا 36 ألف كتابة، متضمنة بعض مشغلات التقارير. عند 50 ألف مستند قابل للنسخ يوميًا تضيف النسخ 1.5 مليون قراءة/30 يومًا. هذا يوضح أن فتح الخزنة cold والتقرير والنسخ أكبر عناصر هذا المثال، وليس تقليل الصفوف المعروضة حلًا لها.

للتحسس الحسابي فقط، جدول Google الرسمي الذي أمكن استرجاعه وقت المراجعة يعرض $0.03 لكل 100 ألف قراءة و$0.09 لكل 100 ألف كتابة و$0.01 لكل 100 ألف حذف. باستخدام هذه الأسعار النموذجية: 4.81 مليون قراءة ≈ $1.44، و36 ألف كتابة ≈ $0.032، **قبل** أي حصة مجانية، وبدون مساحة البيانات/الفهارس، Cloud Run، Storage، الشبكة، Eventarc، Scheduler، بناء ونشر الصور أو Judge0. لم تُثبت منطقة قاعدة البيانات في الحساب، وتعذر فتح محدد مناطق التسعير؛ منطقة Functions في الكود europe-west1 لا تثبت منطقة Firestore. لا تستخدم هذه الأرقام كعرض سعر لفاتورة المنصة.
